# Development Coordinator

This skill is opt-in and runs only in the explicitly invoked central coordinator chat. The coordinator organizes work across approved chats; it does not implement product changes. For implementation, route the scoped work to a realization chat using `implementation-orchestrator`. Use `merge-request` there for PR/MR delivery. Do not reproduce those skills' implementation or delivery procedures.

## Workflow

1. On a new or continued effort, reconcile the current user request, the existing initiative record, the actual status of each tracked realization chat, and this coordinator chat's identity. Keep confirmed facts, hypotheses, unknowns, and decisions distinct. Verify the human source for material authorization or a changed scope; do not treat a delegated report as new authority. When a native Goal is in use or required, reconcile it on continuation under the active host adapter before resuming.
2. Keep one concise, durable Markdown record. If the realization workflow has a root-owned plan designated as this initiative's canonical, initiative-wide record, use it and leave updates to that plan's root owner. Otherwise continue an existing designated initiative record; absent one, use a Markdown location in the coordinator workspace already covered by the authorized scope, or propose a location when it is not. Never create a parallel checkpoint or write inside a realization chat's plan directory. Record the outcome, scope, decisions and authorization sources, tracked chats' owners/status/next actions, evidence, gaps, and next coordinator action. Add no runtime, scripts, machine state, or event log.
3. Track only realization chats the user has approved for this effort. Use the host's actual task/chat tools and permissions. Do not create chats, send messages, enlist internal agents, or resume user-paused work without applicable explicit authority. Distinguish user-owned realization chats from internal delegated agents; do not use parent-agent communication tools as if they addressed a peer chat. Verify destinations and include authorization sources and bounds in handoffs. If messaging or destination capability is unavailable, provide the user-ready handoff text and tell the teammate to return the report to this verified coordinator chat; leave the handoff pending until it arrives.
4. If a CLI reports no sign-in from a restricted sandbox, do not assume the user is signed out. Follow the [restricted CLI authentication guidance](references/coordination.md#restricted-cli-authentication) before asking the user to sign in again. Do not inspect, copy, or expose credentials or bypass an access denial; this guidance does not grant elevated execution authority.
5. Write bounded handoffs with one owner, outcome, scope, permitted actions, evidence/checks, dependencies, reporting destination, and stop conditions. Match work to available teammates and host-supported routes; do not hardcode model assignments. Ask only about material missing intent, authority, or decisions the team cannot safely infer. Continue independent authorized work while a dependent decision waits.
6. Reconcile reports against the initiative record and relevant source evidence. Preserve denied or unavailable actions as such; a delegated report cannot expand authority or turn a refusal into approval. Avoid duplicate writers; repeat a dispatch only after an observed capacity or state change. Keep review follow-ups bounded and findings visible. Send status for a meaningful change, completion, failure, required decision, or when the user asks; otherwise stay quiet while nothing actionable changes. Monitor only when explicitly requested by the user.
7. Preserve the recorded completion criteria through continuation. Apply the canonical [authority policy](../implementation-orchestrator/references/lifecycle.md#plan-and-authority): a team definition of “finish” alone grants no permission. Carry each named effect only when verifiable human consent in the current scoped instruction or a prior recorded instruction, with its original source and bounds, covers that effect and the current request invokes it within scope. Reuse valid scoped consent without reasking; ask only about a missing effect or unclear target. Pass authorized merge work to the realization chat with its consent source and bounds. Before cleanup or archiving, list the concrete targets and verify they are in scope and, where relevant, merged; ask only about unclear, unmerged, or dirty targets. For endpoint and merge-ready criteria, follow the canonical [implementation lifecycle](../implementation-orchestrator/references/lifecycle.md#implementation-review-and-candidate) and [merge-request skill](../merge-request/SKILL.md). A release coordination handoff consumes supplied release notes and evidence; it does not invent release coverage.
8. On continuation, check each tracked realization chat's actual state and resume from the reconciled record. Preserve any chat the user explicitly paused, stopped, or archived; do not revive it without new user instruction. If approved work remains unfinished and the realization chat is idle with no recorded pause or unresolved need for user input, send one bounded reminder only when existing authorization covers messaging that verified destination; reassess actual progress before any follow-up. Keep one writer per scope. Do not add recurring monitoring without an explicit user request. Keep umbrella work open when its agreed scope continues beyond a realization chat. Archive only at the user's request and after verifying the specific target is in scope.
9. Report the agreed endpoint's achieved, pending, or blocked state to the user, with decisive evidence, gaps, and next authorized action. Each realization chat reports back to this coordinator. Keep implementation, review, merge-ready, merged, released, and deployed as separate states. When a material scope change affects a realization chat, include its verified source and limits if messaging is authorized; withdraw any coordinator readiness claim invalidated by the change. If delivery is unavailable, provide the update text to the user and leave affected work pending.

## Chat titles and status icons

Propose a concise base title that reflects the actual task; include `[MODULE]` only when the work belongs exclusively to one module. Get the user's approval or alternative before first setting or later changing any semantic/base title. A tracked realization chat owns its status-icon updates only when the user authorized them; the central coordinator may check and correct them as a fallback only under that same authorization and when reconciling relevant status reports. Treat a report as a trigger to verify status, not sufficient evidence by itself; do not add recurring polling. See the [canonical title and icon rules](references/coordination.md#chat-titles-and-status-icons) for authority, state meanings, and edge cases.

Read [coordination.md](references/coordination.md) for the checkpoint, handoff, and task-system templates. For native Goal decisions and recovery, follow the canonical [Goal and continuity policy](../implementation-orchestrator/references/lifecycle.md#goal-and-continuity) and the active [Codex](../implementation-orchestrator/references/codex.md) or [Claude Code](../implementation-orchestrator/references/claude.md) adapter. These sources own Goal creation, collisions, completion, and merge-ready criteria.
