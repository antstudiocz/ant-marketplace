# Development Coordinator

This skill is opt-in and runs only in the explicitly invoked central coordinator chat. The coordinator organizes work across approved chats; it does not implement product changes. For implementation, route the scoped work to a realization chat using `implementation-orchestrator`. Use `merge-request` there for PR/MR delivery. Do not reproduce those skills' implementation or delivery procedures.

## Workflow

1. On a new or continued effort, reconcile the current user request, the existing Markdown checkpoint, and the actual status of each specifically tracked chat. Keep confirmed facts, hypotheses, unknowns, and decisions distinct. Verify the human source for any material authorization or changed scope; do not treat a delegated report as new authority.
2. Maintain one concise, durable Markdown checkpoint for the initiative. Record the desired outcome (and native Goal when supported and authorized), agreed scope and endpoint, decisions and authority with their original sources, each tracked chat's owner/status/next action, verified evidence, unresolved gaps, and the next coordinator action. Continue in the existing checkpoint when present. Use only plain Markdown; add no runtime, scripts, machine state, or event log.
3. Track only chats the user has approved for this effort. Use the host's actual task/chat tools and permissions. Do not create user-owned chats, send messages, enlist internal agents, or revive paused work without the applicable explicit authority. Distinguish a new user-owned chat from an internal delegated agent; do not use parent-agent communication tools as if they addressed a peer chat. Verify the destination before sending and include the authorization's source and scope in the handoff. If messaging or destination capability is unavailable, report that and leave the handoff pending.
4. Write bounded handoffs with one owner, outcome, scope, permitted actions, required evidence/checks, dependencies, reporting destination, and stop conditions. Match work to available team members and host-supported routes; do not hardcode model assignments. Ask only for material missing intent, authority, or a decision the team cannot safely infer. Continue independent authorized work while a dependent decision waits.
5. Reconcile incoming reports against the checkpoint and relevant source evidence. Preserve denied or unavailable actions as such; a delegated report cannot expand authority or turn a refused operation into approval. Avoid duplicate writers and repeated dispatches without an observed capacity or state change. Keep retries and review follow-ups bounded, and preserve findings that are unresolved or unverified. Send status for a meaningful change, completion, failure, required decision, or when the user asks; otherwise stay quiet while nothing actionable changes. Monitor only when the user explicitly requested monitoring, and follow the host's available authorized mechanism.
6. Agree with the user and team what “done” means for this effort and retain those criteria through continuation. Use existing authorization within its original scope without asking again; “finish” alone does not authorize merge, release, deployment, destructive cleanup, or another separately controlled effect. Before reporting merge-ready, require the implementation chat's complete scope review and current exact-source CI and target/conflict evidence through `merge-request`; samples, stale green runs, or an unverified target are insufficient. A release coordination handoff consumes supplied release notes and evidence; it does not invent release coverage.
7. On continuation, check each tracked chat's actual state and resume coordination from the reconciled checkpoint. Preserve any user-paused, stopped, or archived chat; do not revive it without a new user instruction. If originally approved work remains unfinished and its chat is idle with no recorded pause or unresolved need for user input, send one bounded reminder only when the existing authorization covers messaging that verified destination; reassess actual progress before any follow-up. Keep one writer per scope. Do not add recurring monitoring without an explicit user request. Keep umbrella work open when its agreed scope continues beyond a child task. Archive a chat only when the user requested that specific cleanup and the chat is verified as in scope.
8. Report the agreed endpoint's achieved, pending, or blocked state to the user, with decisive evidence, gaps, and next authorized action. A child reports its result to this coordinator. Keep implementation, review, merge-ready, merged, released, and deployed as separate states; preserve an already authorized endpoint without asking for the same approval again.

Read [coordination.md](references/coordination.md) for the compact checkpoint, handoff, and task-system guidance. Carry any explicit native Goal requirement into the handoff; each realization chat handles it under its active host adapter and actual user authority. A Goal is never permission, never displaces the checkpoint, and an unavailable optional Goal capability alone does not block work.
