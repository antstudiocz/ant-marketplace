# Worked review scenarios

These small manual examples check how the [review policy](review.md) is applied. Inputs and expected decisions below are examples; they are not executed tests or evidence of a real review.

- **Specialist selection** — Input: a SQL migration changes a query and a separate edit changes only a label. Expected: select data/SQL review for the migration; do not add specialists for the label-only edit by default.
- **Independent first pass** — Input: a frozen candidate, task objective, contracts, and outcome evidence are ready; the implementer says the patch is correct and another reviewer has findings. Expected: give the overall reviewer the objective, candidate, contracts, and evidence without either conclusion.
- **Finding disposition** — Input: a focused reproduction disproves a reported failure; another provider path cannot be accessed. Expected: mark the first finding refuted with reproduction evidence; mark the second unverified and retain the access gap.
- **Author differs from root** — Input: an OpenAI integration owner works under a Claude root. Expected: record OpenAI as source-author provider and route the overall review to Anthropic.
- **Explicit model conflicts** — Input: the user selected an OpenAI reviewer for OpenAI-authored work. Expected: honor the selection and report cross-provider review as unmet; ask the user only if the consequence leaves a genuinely unresolved decision. Do not substitute Anthropic automatically.
- **Mixed authorship** — Input: consequential implementation changes came from both OpenAI and Anthropic owners. Expected: route review so each contribution has opposite-provider coverage, or report the uncovered portion.
- **Other provider unavailable** — Input: the implementation is OpenAI-authored and no verified Anthropic review route is available. Expected: report cross-provider coverage as unavailable or unverified and leave the required review outcome pending; do not substitute a same-provider review.
- **Finding severity and readiness** — Input: one reviewer reports a credible potential data-loss trigger with material impact, but a bounded reproduction is inconclusive. Expected: retain it as unverified, have root adjudicate evidence and impact, and do not mark the affected outcome achieved solely because reproduction failed; a draft may proceed with the gap stated.
- **Host denial** — Input: the host refuses the selected cross-provider review operation. Expected: do not route the same operation through another tool; continue other authorized work and report review as pending.
- **Real browser flow** — Input: a changed flow supports create, reuse, and repeat requests; an API response and screenshot are available but no interaction was performed. Expected: exercise relevant browser interactions for create/reuse/repeat and verify provider processing when in scope; the response and screenshot alone do not prove the flow.
- **Evidence invalidation** — Input: a docs-only candidate change follows a browser smoke, with no impact path to the exercised flow; alternatively, the request path changes. Expected: retain the earlier smoke only for the docs-only change with that impact rationale; rerun affected flow evidence after the request-path change.
